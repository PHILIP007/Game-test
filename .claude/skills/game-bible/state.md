# State: store, transitions, actions, runtime

Four roles, each in its own module (the starter's `store.ts`, `actions.ts` and `runtime.ts` show the shape):

- **Store**: vanilla zustand stores holding **plain data only**, with no function properties. There's one for game state (with meta), persisted through `persist` and zod-validated on rehydrate, and a separate one for UI state that is never persisted. Read with `getState()` or a subscription. Replace state through `setState`, never mutate it in place: persist saves only on a set. zod runs in persist's `merge` (a save that fails keeps the default), and a custom `PersistStorage` can keep one raw key per saved slice instead of persist's `{state, version}` blob. Persist doesn't write after hydrating (only when migrating), so write once at boot if a save's presence matters (first launch): `store.setState((s) => s)` does it, since persist's wrapped `setState` always saves even when zustand skips the notify.
- **Transitions**: pure `(state, ...args) → next`, and nothing hidden. Impurities (now, fresh ids, a new seed) arrive as arguments. Only transitions with real logic get a function: something that branches, keeps an invariant across fields, or does math. On a no-op, return the same reference so subscribers skip the notify. Queries (functions that answer a question) take no verb and no prefix. In a game, the core's rule verbs *are* the transitions (`playMeld(prev, ids)`); a UI store's transitions are named `with*`/`without*` (the state with this change).
- **Actions**: `actions.ts` is the one impure boundary for state. It uses imperative verb names, reaches the core through a namespace (`import * as Game from './game'`, then `Game.playMeld`) so the layer shows at the call site, and inlines trivial single-field writes (`setState({ screen: 'camp' })`) rather than wrapping them. Screens and input handlers import actions directly; a tap handler calls an action and never mutates state.
- **Runtime**: anything whose lifetime is the game's (ticker, input listeners, audio, save subscription) starts in one place and returns its disposer.
- **What goes in the UI store, what stays in the shell**: the UI store holds what a screen binds or an action decides: the current screen, open panels, selections, the toast. The render subscribes to it, so every write redraws, and writing it while drawing is a bug (make the render throw on it). Per-frame gesture scratch stays module-local in the shell module that owns the gesture: the drag in flight, scroll offsets and velocity, hit rectangles, sprite handles. It changes on every pointermove, nothing binds it, and a store write there would redraw every frame. A tap handler changes its local scratch first and then makes one action call. A run start that must also drop shell scratch hears it through an action listener (`Actions.onStart`), which may not write UI state itself.
